## Verified tagged-source behaviour

In [obspy-readbuffer.c](https://raw.githubusercontent.com/obspy/obspy/1.5.1/obspy/io/mseed/src/obspy-readbuffer.c), `readMSEEDBuffer` starts by parsing records with payload unpacking disabled. It traverses an offset through the supplied buffer, but includes blank/non-SEED skip paths, truncated-tail breaks and a missing-Blockette-1000 fallback using the remaining size (lines 281–425). It is therefore a permissive reader, not the study's strict sequential structural admission gate. Reject those shapes before vendor invocation rather than accepting the subset the reader returns.

The same function retains a linked list of records, then groups them through linked identity and segment lists. Each record can search the existing identities, so the work can grow with both record count and identity count (lines 517 onward). The source has no study record, identity, sample or wall-time budget. Length and advertised-count limits must be imposed outside it; a parent-frozen routing scope and contained worker deadline still matter.

When payload decode is requested, `msr_unpack_data` is called for each record before the Python allocation callback (lines 486–495). The record's C sample buffer remains attached while records are accumulated. At the later segment merge, the C function calls `allocData` with the segment's advertised sample total and sample type, copies record buffers into that destination, then frees each record's native sample buffer (661–688). Consequently the Python callback does not cover all sample allocation: native per-record arrays exist before it, and record arrays overlap in lifetime with the segment destination. The callback argument has C `int` width while segment totals are wider; the proposed 8,000,000-sample body cap is below signed-int range, but this is a future validated profile, not proof about arbitrary input.

In [unpack.c](https://raw.githubusercontent.com/obspy/obspy/1.5.1/obspy/io/mseed/src/libmseed/unpack.c), `msr_unpack` copies/allocates the fixed header and sets the advertised sample count from it. It traverses and allocates blockette structures. It has next-link/record checks, but some irregularities only warn or break the loop; blockette-count and data-start disagreement are warnings. Blockette 1000 sets record length by a shift and populates encoding/word order. The strict scanner must validate exponent, current-record extents, link count, unique 1000, count equality and data-start separation before any of those branches, rather than relying on a warning as rejection.

`msr_unpack_data` checks a record's data offset and computes its native output allocation from advertised sample count times output sample width. INT16, INT32, FLOAT32 and STEIM outputs use four bytes per sample; FLOAT64 uses eight. It reallocates that buffer before calling the encoding-specific decoder (722–815). The fixed-width decoder calls receive a pointer and sample count/output size rather than the current record's input byte span; the scanner must independently prove fixed-width samples fit inside the payload. STEIM calls also receive the payload byte span, but their subdecoder bodies were not fetched or inspected. These two files alone do not establish complete STEIM malformed-input safety.

The wrapper merge uses a tolerance of roughly half a sample period, a rate tolerance and segment grouping. Segment encoding, word order and record length annotations come from the first record, and the sample period uses a floating division followed by integer conversion. Coalesced traces and their first-record descriptors cannot certify each raw record or an exact nanosecond sample lattice. `raw_record_timing_verified` remains false.

The tagged source can read environment overrides for header/data byte order and encoding, including fallback encoding. A future isolated worker must freeze/clear those overrides before importing the decoder, and use the scanner's verified uniform header-byte-order/length settings explicitly. This is an environment-control design requirement, not an environment inspection or mutation performed here.

## Minimal recommended route and remaining gates

Keep the prior authored structural scanner recommendation: one immutable positively pinned body; data records only; strict literal identities; unique explicit Blockette 1000; exponent 8–20; exact contiguous record boundaries; bounded forward non-overlapping blockettes; initially only verified 100/1000/1001 layouts; encoding whitelist 1/3/4/5/10/11; independent advertised-count sum; and no skipping, fallback, silent tail discard or convenient replacement. Exact optional layout sizes and STEIM frame admission still require prospective specification/tests. If they remain unresolved, retain those formats as gated unknowns rather than pass them to a decoder.

Retain 8 MiB raw per body, 17 bodies, one body at a time, 32,768 records/body, at most 16 blockette links/record and proposed 8,000,000 samples/body. The 32*N planning term in the earlier envelope can provisionally cover native record samples, a segment destination and further arrays/copies, but these sources do not prove that four eight-byte copies bound every allocation. MSRecord/blockette allocator helpers, parsing internals, encoding subdecoders, Python/native temporary arrays, allocator fragmentation and compiled binary behaviour remain outside this bounded inspection. Advertised sums constrain expected allocations, not all possible malformed-input behaviour.

Use an independently verified isolated worker memory/address-space control, bounded output and wall-time limit for future payload decode. A callback-only check, `headonly`, a timeout or post-decode RSS observation is insufficient. Whole decoder errors, warnings that violate the frozen profile, count/identity/record discrepancies, crashes and limit kills must yield retained unknown outcomes. Python `_read_mseed` has an `InternalMSEEDError` handling path; the complete C logging wrapper and compiled runtime correspondence were not audited here, so do not claim that every malformed branch raises safely before allocation.

The parent must positively pin the actual Python/native runtime, validate immutable scanner-to-decoder handoff and demonstrate effective resource controls on invented over-budget cases before actual use. Tag name and source retrieval are not a proof that the installed compiled library was built from these exact bytes. No installed/tagged Python byte comparison was made: the fetched URLs are C files, not the installed Python modules pinned by the prior audit. No current EarthScope libmseed version was substituted.

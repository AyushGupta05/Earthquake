# MiniSEED admission source audit — advisory only

This packet recommends a small authored structural MiniSEEDv2 scanner before payload decoding. Neither ObsPy's `get_record_information` nor `headonly=True` is a complete bounded admission gate. Source-native record clocks, decompression admission and hard RSS control remain unverified. Actual payload decoding is barred until a separate prospective implementation, review and containment test closes those gates.

Scope is source inspection and design only. Three installed Python source files were inspected; two official source URL opens failed. No ObsPy import, vendor execution, generated binary, decoder call, actual body or private research input was used. The parent supplied the ObsPy 1.5.1 / Python 3.14 runtime label. This audit pins three Python files, not the runtime, compiled decoder or binary-to-source correspondence. No vendor source is copied into this packet.

## What the inspected source supports

The installed `obspy/io/mseed/util.py` APIs `get_record_information` and `_get_record_information` inspect the first record at the requested position (lines 504–544 and 569 onward). The helper can reset the requested start, recurse across padding, or scan full-SEED controls. Its blockette chain checks forward progress, but does not enforce an application blockette-count or current-record byte bound before each seek. Blockette 1000 supplies encoding and a power-of-two record length. Without it, the helper invokes the C `ms_detect` path on a small input buffer. Its reported `number_of_records` is remaining file size divided by the first record length (lines 817–819), rather than an enumeration of each record and the sum of their sample counts. This cannot certify heterogeneous records or an advertised total.

The same utility strips identity fields and can discard non-ASCII bytes with a warning; it can warn rather than reject inconsistent word-order information. Its date parsing and corrections include floating operations. A future admission scanner must use strict identities and explicit structural acceptance, and must not turn these date calculations into an exact nanosecond claim. Header byte order and payload word order are distinct fields.

In `obspy/io/mseed/core.py`, `_read_mseed` loads its complete input (lines 458–469). `headonly=True` requests no payload unpacking (413–416), but still enters `clibmseed.readMSEEDBuffer` (668–671). The Python allocation callback uses `np.empty(samplecount, dtype=...)` and retains the allocated arrays (647–655); it has no study sample-budget check. The reader can concatenate chunks and form coalesced trace objects. Header-only traces therefore do not provide an independent raw-record timing proof or a bound on C linked-record/segment allocation.

`obspy/io/mseed/headers.py` describes numeric allocation dtypes of up to eight bytes per sample, a supported record-length list from 256 bytes through 1 MiB, and the encoding mapping. An INT16 input can use the int32 allocation dtype. The local compiled reader's internal allocations, record expansion, malformed-input paths and matching source were not verified. The installed candidate C sources were absent; the two official tagged-source opens failed. That unresolved limit is material, not a successful audit of the C path.

## Minimal future route

Use an authored, standard-library structural scanner over one immutable, positively pinned raw body. It must never import ObsPy, resynchronize, search for a more convenient record, recurse, call `ms_detect`, read a file itself, or allocate payload arrays. Sequential record enumeration reads bounded fixed/header fields, extracts each advertised `npts`, and sums them with integer arithmetic before admitting any payload decode. A byte view may avoid copying the raw body; its descriptor output must also be bounded.

The initial prospective profile in PROFILE_TESTS.md deliberately accepts only a narrow explicit MiniSEEDv2 record layout. Unsupported format, ambiguous headers or broken structure remains a retained unknown outcome. This does not establish physical absence, change an original target, or earn a retry. The parent must freeze this profile before implementation; it is not yet a normative protocol.

After admission, use only the pinned installed decoder in a separately contained worker, with exactly the scanned immutable bytes. Standard ObsPy's exposed reader does not accept a study budget in its local allocation callback. Consequently an advertised-count ledger alone is insufficient. Either an independently verified guarded decoder admission adapter or verified OS-enforced memory containment must cover allocations before actual payload use. No vendor patch or adapter is implemented or proposed for execution in this packet. A timeout, polling watchdog, raw-byte cap, post-decode trace check, or `headonly` pass is not a hard memory limit.

The smallest recommended initial path is: bounded parent raw loading and custody verification; pure structural header scan; verified immutable handoff; contained standard ObsPy decode; declared-versus-decoded ledger reconciliation; exact causal-prefix qualification under the separate frozen qualifier protocol. A decode crash, limit kill, disagreement or unknown allocation path is retained as unknown. No partially completed worker output is promoted to success. A validated control must exist before step four.

## Suggested prospective caps; no RSS proof

Keep 8 MiB maximum per raw body, at most 17 bodies (136 MiB aggregate raw maximum), one batch/body processed at a time, and no retained decoded arrays across batches. The profile's minimum 256-byte records implies a maximum of 32,768 records per body. A proposed ceiling of 16 blockette links per record permits at most 524,288 bounded links per body. These are fixed before results.

Propose 8,000,000 advertised samples per body and 136,000,000 over all 17 bodies. Check both before payload decode. The unsigned 16-bit count in each fixed header alone is inadequate: a small compressed body can advertise a much larger expansion. Keep metadata/routing qualification independent of this sample admission decision.

For root consideration, a planning envelope is `32*N + 16 MiB + 2 KiB*R + 4 KiB*T + 256 MiB`, where N is admitted advertised samples, R is enumerated records and T is a proposed decoded-trace ceiling no larger than R. The 32*N term provisionally budgets four simultaneous eight-byte sample copies; 16 MiB budgets raw bytes and one decoder input copy. At the proposed maxima this is about 708 MiB, before additional unknown native allocator overhead. A 1 GiB worker limit is a proposed starting control with margin, not a demonstrated sufficient or effective limit. The per-record, per-trace and baseline amounts are conservative planning assumptions, not measured allocations. Coalescence, C structures, allocator behaviour and temporary copies may violate them.

Before actual use, the parent must verify runtime/compiled-library pins, strict scanner cap behaviour, descriptor/output bounds, declared expansion checks and effective process containment. A future Linux cgroup memory limit and disabled swap could be evaluated, but their enforcement must be demonstrated in the chosen environment, including a deliberately over-budget synthetic worker. No such control is configured or tested here. Any hard RSS or decompression gate not verified keeps actual payload decoding barred.
